# Git Commit Scenario

## 목적

이 문서는 사용자가 현재 작업한 내용을 커밋하려고 할 때,
AI 에이전트와 어떤 순서로 협업하는지 보여주는 시나리오 예시다.

## 시나리오

개발자가 작업을 마친 뒤, 커밋할 파일만 직접 stage에 올린다.
그 다음 AI 에이전트에게 이렇게 요청한다.

> 지금 stage에 올린 변경 기준으로 커밋 초안 만들어줘.
> 그리고 현재 브랜치에서 바로 커밋해도 되는지도 같이 봐줘.

## 진행 흐름

### 1. 사용자가 stage 범위를 정한다

이 단계는 사용자가 직접 한다.

예:

- 필요한 파일만 `git add` 한다.
- 아직 커밋하고 싶지 않은 변경은 stage에 올리지 않는다.

이렇게 하면 AI 에이전트는 전체 작업 디렉토리가 아니라,
사용자가 선택한 변경만 기준으로 이력 초안을 만들 수 있다.

### 2. AI 에이전트가 이력과 커밋 초안을 만든다

AI 에이전트는 stage된 변경을 읽고 아래 내용을 정리한다.

- 무엇이 바뀌었는지
- 왜 이 변경이 필요한지
- 어떤 식으로 이력 제목, 이력 내용, 커밋 메시지를 쓰면 좋을지

예를 들어 이런 초안이 나올 수 있다.

- 이력 제목 초안:
```text
[설정] k8s 설정 추가 변경
```
- 이력 내용 초안:
```text
- k8s 배포 설정 파일을 추가함
- 환경별 설정 분리를 위해 values 구성을 정리함
- 기존 배포 흐름은 유지함
```
- 커밋 제목 초안: `[#이력번호] [설정] k8s 설정 추가 변경`
- 브랜치 초안: `이력번호-k8s-config-update`

이 단계에서 AI 에이전트는 이력번호를 임의로 채우지 않고,
자리표시자 형태로만 제안한다.

### 3. 사용자가 이력 번호와 최종 메시지를 정한다

사용자는 AI가 준 초안을 그대로 쓰지 않고,
자기 기준에 맞게 다듬은 뒤 최종 이력 번호와 메시지를 정한다.

예:

- 이력 번호: `13`
- 이력 제목:
```text
[설정] k8s 설정 추가 변경
```
- 이력 내용:
```text
- k8s 배포 설정 파일을 추가함
- 환경별 설정 분리를 위해 values 구성을 정리함
- 기존 배포 흐름은 유지함
```
- 최종 커밋 제목: `[#13] [설정] k8s 설정 추가 변경`
- 최종 브랜치명: `13-k8s-config-update`

이 단계는 사용자가 직접 검토하는 것이 중요하다.

## 4. AI 에이전트가 브랜치를 확인한다

커밋 전에 AI 에이전트는 현재 브랜치가 작업 브랜치인지 확인한다.

예를 들어 아래 같은 상황을 본다.

- 현재 브랜치가 `main`인지
- 현재 브랜치가 이미 작업 브랜치인지
- 새 브랜치를 만드는 편이 안전한지

작업 브랜치가 아니라면,
사용자가 정한 이력 번호와 이력 제목을 바탕으로 새 브랜치를 만든 뒤 그 브랜치에서 커밋을 진행한다.

예시 브랜치명:

- `13-k8s-config-update`

### 5. 사용자가 최종 커밋을 요청한다

브랜치와 메시지가 정리된 뒤,
사용자가 명시적으로 "이 메시지로 커밋해줘"라고 요청하면 AI 에이전트가 커밋을 진행한다.

## 이 시나리오가 보여주는 점

이 구조에서는 아래 역할이 분리된다.

- 사용자는 stage 범위와 최종 이력 메시지를 책임진다.
- AI 에이전트는 staged diff 기반 요약, 초안 작성, 브랜치 안전성 확인을 돕는다.

그래서 사람 입장에서는 아래 장점이 있다.

- 커밋 범위를 스스로 통제할 수 있다.
- AI가 초안을 도와주지만 최종 이력 품질은 직접 보장할 수 있다.
- 실수로 기본 브랜치에 바로 커밋하는 위험을 줄일 수 있다.
