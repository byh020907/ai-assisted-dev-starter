# Feature Development Example

## 목적

이 문서는 이미 진행 중인 프로젝트에서 사람이 새로운 기능 개발을 요청했을 때,
AI 에이전트가 현재 프로젝트 규칙을 참고해 어떻게 작업 문서를 만들고 이어가는지 보여주는 시나리오 예시다.

## 시나리오

개발자가 TODO 목록에 아래 요청을 남긴다.

> 날짜별로 메모를 조회할 수 있는 기능이 필요해.
> 기존 규칙에 맞춰 작업 문서도 같이 만들어줘.

AI 에이전트는 현재 프로젝트의 문서 구조와 지침을 확인한 뒤,
이 요청을 하나의 feature 작업으로 보고 관련 문서를 준비한다.

## 이 요청 이후 생기는 문서

```text
+docs/tasks/20260311-add-date-filter/
+|-- task.md
+|-- worklog.md
+`-- decision.md
```

## 작업이 진행되는 방식

### 1. task.md 생성

AI 에이전트는 먼저 `task.md`를 만들고 이번 기능의 범위를 정리한다.

예를 들어 아래 같은 내용이 들어간다.

- 날짜별 메모 조회 기능 추가
- 날짜 필터 파라미터 정의
- 완료 조건과 제외 범위 정리

이 문서 덕분에 개발자는 "이번 작업에서 어디까지 할지"를 바로 확인할 수 있다.

### 2. worklog.md 기록

개발이 진행되면서 AI 에이전트는 `worklog.md`에 중간 확인 내용을 남긴다.

예:

- 현재 메모 조회 API 구조 확인
- 날짜 필터를 query parameter로 둘지 검토
- 타임존 처리 이슈 확인
- 검증 결과와 보류 사항 기록

이 문서는 세션이 바뀌거나 다른 사람이 이어받아도 흐름을 이해할 수 있게 도와준다.

### 3. decision.md 기록

기능 구현 중 중요한 선택이 생기면 `decision.md`에 남긴다.

예:

- 날짜 필터는 `createdAt` 기준으로 처리한다.
- 필터 입력 형식은 `YYYY-MM-DD`로 통일한다.
- 타임존은 서버 기준이 아니라 요청 기준 UTC로 해석한다.

이 문서는 나중에 "왜 이런 방식으로 구현됐는지"를 이해하는 기준이 된다.

## 사람 입장에서 이 구조가 주는 장점

사람은 기능 요청만 해도, AI 에이전트가 현재 지침에 맞는 문서 구조를 먼저 만든다.
그래서 개발자는 아래를 쉽게 확인할 수 있다.

- 지금 어떤 작업이 진행 중인지
- 이번 기능의 범위가 어디까지인지
- 중간에 어떤 판단이 있었는지
- 나중에 어떤 결정을 되짚어봐야 하는지

## ADR과의 구분

이 시나리오의 `decision.md`는 이번 날짜 조회 기능 안에서 나온 선택을 기록하는 문서다.
반면 프로젝트 전체의 장기 기준을 바꾸는 결정은 `docs/adr/`에 남긴다.

예:

- `decision.md`: 날짜 필터를 어떤 형식으로 받을지
- `docs/adr/`: 앞으로 모든 조회 기능에서 날짜 필터 정책을 공통 기준으로 삼을지
